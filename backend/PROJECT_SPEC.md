# Техническая спецификация: Smart Hydroponics Management API

Документ описывает целевую архитектуру и фактическую реализацию в репозитории на момент составления. Исходный текст раздела «Контекст и границы системы» из запроса не был приложён; при необходимости его можно вставить в раздел 1 как дополнение к нижеследующему.

## 1. Обзор системы

### 1.1. Цель

**Smart Hydroponics Management API** — бэкенд «цифрового двойника» гидропонной установки: **единая точка правды** для состояния **полок (shelves)** — агрегатов, объединяющих телеметрию датчиков и исполнительные устройства. Система связывает поток данных с ESP32 с мобильным клиентом (Flutter) и служит источником агрегированных снимков для дашборда.

### 1.2. Границы системы

| В зоне ответственности API | Вне зоны (интеграции / клиенты) |
|---------------------------|----------------------------------|
| Хранение и выдача состояния полок, логов датчиков, исполнительного состояния | Прошивка ESP32, сеть между устройством и API |
| Приём телеметрии (`POST /sensors/report`) | Обучение/инференс ML-моделей «ИИ» (флаг `is_ai_mode` — доменное соглашение) |
| Расчёт производных величин на сервере (например, VPD для `/current`) | Real-time push до клиента (в текущей версии отсутствует) |
| HTTP JSON API | Аутентификация и авторизация (в коде не реализованы) |

### 1.3. Ключевые сущности предметной области

- **Полка (Shelf)** — логическая единица мониторинга и управления с именем и индикатором статуса (`OK` / `WARNING` / `CRITICAL`) для «светофора» дашборда.
- **Лог датчика (SensorLog)** — временной ряд измерений: температура, влажность, CO₂, TVOC.
- **Состояние устройств (DeviceState)** — текущие уставки и режимы исполнителей на полку, включая режим ИИ (`is_ai_mode`).

## 2. Технологический стек

| Компонент | Назначение | Детали в проекте |
|-----------|------------|------------------|
| **FastAPI** | HTTP API, валидация запросов/ответов, OpenAPI | Точка входа `app/main.py`, роутеры в `app/api/routes/` |

## 3. Архитектура бэкенда

### 3.1. Слоистая структура

```text
┌─────────────────────────────────────────────────────────┐
│  HTTP (FastAPI) — маршруты, зависимости, коды ответов   │
├─────────────────────────────────────────────────────────┤
│  Schemas (Pydantic) — контракт входа/выхода API         │
├─────────────────────────────────────────────────────────┤
│  Models (SQLAlchemy ORM) — таблицы, связи, инварианты   │
├─────────────────────────────────────────────────────────┤
│  Core — конфигурация, утилиты (напр. расчёт VPD)        │
├─────────────────────────────────────────────────────────┤
│  DB session — async engine, sessionmaker, yield session │
└─────────────────────────────────────────────────────────┘
```

- **`app/main.py`** — создание приложения, CORS, **lifespan**: при старте выполняется `Base.metadata.create_all` и совместимостный `ALTER TABLE` для колонки `target_temperature`.
- **`app/api/router.py`** — агрегирование подроутеров: `dashboard`, `shelves`, `sensors`.
- **`app/api/routes/*.py`** — обработчики эндпоинтов; бизнес-правила уровня HTTP (например, конфликт при ручном управлении в режиме ИИ).
- **`app/models/`** — декларативные ORM-модели и перечисления.
- **`app/schemas/`** — DTO для сериализации и валидации тел запросов/ответов.
- **`app/db/session.py`** — `create_async_engine`, `async_sessionmaker`, генератор сессии.
- **`app/core/`** — `Settings`, `calculate_vpd`.

### 3.2. Dependency Injection для сессий БД

Паттерн: **одна сессия на один HTTP-запрос**, получаемая через зависимость FastAPI.

1. **`get_db_session()`** (`app/db/session.py`) — async generator: открывает `AsyncSessionLocal()`, отдаёт сессию в `yield`, после завершения запроса контекст менеджера закрывает сессию.
2. **`get_session()`** (`app/api/deps.py`) — тонкая обёртка, пробрасывающая тот же поток сессий (удобная точка для будущих cross-cutting зависимостей).
3. В эндпоинтах: `session: AsyncSession = Depends(get_session)`.

Таким образом, роутеры не создают сессии вручную; жизненный цикл привязан к запросу, что упрощает тестирование (подмена `get_session`) и исключает утечки соединений при корректном использовании `commit`/`rollback` в обработчиках.

## 4. Модель данных

### 4.1. Диаграмма связей (Mermaid)

```mermaid
erDiagram
    SHELF ||--o{ SENSOR_LOG : "has many"
    SHELF ||--|| DEVICE_STATE : "has one"

    SHELF {
        int id PK
        string name UK
        shelf_status status
    }

    SENSOR_LOG {
        int id PK
        int shelf_id FK
        float temperature
        float humidity
        int co2
        int tvoc
        timestamptz timestamp
    }

    DEVICE_STATE {
        int shelf_id PK_FK
        int light_brightness
        int fan_speed
        float target_temperature
        bool heater_on
        bool humidifier_on
        bool is_ai_mode
    }
```

- **Shelf 1:N SensorLog** — каскадное удаление при удалении полки (`ondelete="CASCADE"`).
- **Shelf 1:1 DeviceState** — первичный ключ `device_states.shelf_id` совпадает с `shelves.id`; связь `uselist=False`, каскад при удалении полки.

### 4.2. Инварианты и доменная логика

- **Уникальность имени полки** — `Shelf.name` уникален.
- **Статус полки** — `ShelfStatus` хранится как нативный enum PostgreSQL (`shelf_status`).
- **Временные ряды** — `SensorLog.timestamp` с timezone, по умолчанию `now()` на сервере БД.
- **Ограничения валидации API** — частично на уровне Pydantic (например, влажность 0–100 в отчёте датчика, диапазоны для PATCH управления).

#### Режим ИИ: `is_ai_mode`

Поле **`DeviceState.is_ai_mode`** (по умолчанию `True` в модели) задаёт приоритет автоматического управления над ручным.

**Инвариант, реализованный в API** (`PATCH /shelves/{shelf_id}/control`):

- Если **`is_ai_mode == True`**, то **любое** обновление полей, кроме **`is_ai_mode`**, запрещено → ответ **409 Conflict** с текстом о том, что ручное управление отключено.
- Исключение: клиент может передать только смену **`is_ai_mode`** (например, выключить ИИ), после чего остальные поля снова становятся доступны для PATCH.

Это разделяет «выход из режима ИИ» и «ручную настройку исполнителей» без гонок на уровне одного запроса.

## 5. API-контракт

Базовый префикс: роутеры подключаются без общего `/api/v1` (корневые пути ниже — как в приложении).

| Метод и путь | Назначение | Особенности |
|--------------|------------|-------------|
| `GET /` | Проверка живости | `{"status":"ok","service":...}` |
| `GET /dashboard/summary` | Сводка по всем полкам для «светофора» | Список `ShelfSummaryRead` (id, name, status) |
| `GET /shelves/{shelf_id}/current` | Снимок полки: полка + последний лог + устройства + **VPD** | VPD считается из **последнего** `SensorLog` через `calculate_vpd(T, RH)`; если логов нет, `vpd: null`. Поля `latest_sensor` / `device_state` могут быть `null`, если данных нет |
| `GET /shelves/{shelf_id}/logs` | История логов полки | Query `limit` (1–2000, по умолчанию 200), порядок ответа: **от старых к новым** |
| `PATCH /shelves/{shelf_id}/control` | Частичное обновление `DeviceState` | См. раздел 4.2; тело `DeviceStateControlPatch` (все поля опциональны, с ограничениями `ge`/`le` где задано) |
| `POST /sensors/report` | Приём телеметрии от ESP32 | Создаёт `SensorLog`; `timestamp` опционален (иначе UTC «сейчас»); 404, если полки нет |

### 5.1. Расчёт VPD в `/current`

Функция **`calculate_vpd(temperature, humidity)`** (`app/core/utils.py`):

- Использует классическую аппроксимацию давления насыщенного пара по температуре и фактического парциального давления через RH.
- Результат — **дефицит давления пара в кПа**, округление до 3 знаков.
- При некорректной влажности вне [0, 100] — `ValueError` (в текущих путях данные приходят из БД/валидации отчёта).

## 6. Инфраструктура

### 6.1. Docker Compose

В **корне монорепозитория** файл `docker-compose.yml` поднимает **PostgreSQL 16** и сервис **`api`** с `build.context: ./backend`:

- Пользователь/пароль/БД: `postgres` / `postgres` / `hydroponics` (согласовано с дефолтом `Settings.database_url`).
- Порт **5432** на хосте.
- Именованный том **`hydroponics_pg_data`** для персистентности данных.
- **Healthcheck**: `pg_isready` каждые 10 с.

Сервис **API** собирается из `backend/Dockerfile`; для локальной разработки без Docker API по-прежнему можно запускать на хосте из каталога `backend/`.

### 6.2. Инициализация базы данных

1. **Поднять стек**: из корня репозитория — `docker compose up -d` (или только `postgres` для запуска API на хосте).
2. **Переменные окружения** (опционально): в каталоге `backend/` скопировать `.env` из `.env.example`, при необходимости изменить `DATABASE_URL`.
3. **Схема при старте API**: `lifespan` в `app/main.py` вызывает `create_all` для всех таблиц из `Base.metadata` и выполняет **`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`** для обратной совместимости с существующими инсталляциями.
4. **Сиды для разработки**: из `backend/` выполнить `python seed.py` — создаёт БД при отсутствии, таблицы, полки, `DeviceState`, синтетические `SensorLog` за заданное число дней.

Для production **рекомендуется** заменить «create_all + ручной ALTER» на управляемые миграции (см. roadmap).

## 7. Roadmap развития

Ниже — задачи, вытекающие из типичных **нефункциональных требований** к подобным системам и из текущих пробелов кода.

| Приоритет | Задача | Обоснование |
|-----------|--------|-------------|
| Высокий | **Alembic** (миграции схемы) | Версионирование БД, отказ от неявных `ALTER` в lifespan, безопасные деплои |
| Высокий | **Аутентификация / JWT** (или API keys для устройств) | Защита `POST /sensors/report` и `PATCH /control` от несанкционированных изменений |
| Средний | **MQTT (или WebSocket)** для real-time | Снижение опроса HTTP, push событий телеметрии и алертов на Flutter |
| Средний | **Масштабирование таблицы логов** | Партиционирование по времени, архив в холодное хранилище, TTL/агрегаты; индексы по `(shelf_id, timestamp DESC)` |
| Средний | **Доработка контейнеризации API** | Multi-stage build, healthcheck сервиса `api`, CI-образы, secrets вне compose |
| Средний | **Наблюдаемость** | Структурированные логи, метрики (latency, ошибки БД), трассировка |
| Низкий | **Закрепление версий** зависимостей | Воспроизводимые сборки |
| Низкий | **Тесты** (unit + integration с TestClient и БД в Docker) | Регрессии по инвариантам `is_ai_mode` и расчёту VPD |
